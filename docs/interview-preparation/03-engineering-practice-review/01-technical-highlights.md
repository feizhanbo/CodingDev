# 技术亮点重新评估

复杂度评价是本仓库内部相对判断，面试价值取决于能否解释不变量、失败路径和证据，不等于系统达到生产级。

| 候选 | 背景与核心问题 | 实际方案及额外约束 | 复杂度 / 工程价值 / 区分度 | 分类与局限 |
| --- | --- | --- | --- | --- |
| E1 DevPilot 验证 | 模型与被修改测试不能共同定义成功 | 冻结清单、候选副本、独立 suite、visible/hidden 分离、smoke 排除能力指标 | 高 / 高 / 高 | 核心亮点；自然语言条件多数仍 uncovered，同机非恶意代码隔离 |
| E2 DevPilot 恢复 | checkpoint 与文件/模型不处于共同事务 | 回执与摘要、manifest、模型账本、拒绝不确定工具重放 | 高 / 高 / 高 | 核心亮点；不能保证 exactly-once，恢复率受保守策略影响 |
| E3 DevPilot 资源治理 | 单次超时不能约束循环和遗留子进程 | 全局及累计预算、取消 Event、进程树、输出限额、恢复计账 | 高 / 高 / 高 | 核心亮点；非 CPU/内存硬隔离，协作清理可能延迟返回 |

## 能力与证据链

E1 体现对指标真实性和验证信任边界的理解；证据是 `verification/evidence.py`、`TaskVerifier.verify`、`test_evidence.py`。E2 体现失败建模与可恢复性，证据是 `OperationJournal.begin/complete` 和 `test_graph_resume.py`。E3 体现资源所有权，证据是 `RunBudget`、`run_cancellable/run_process` 与 `test_processes.py`。E7 体现业务不变量，证据是 `OrderService`、`transition_status/update_stock` 和订单完整性故障注入测试。

这些能力只能说明项目中有对应实践；个人能否将其作为经历，需要确认贡献并能解释代码。

## 不宜包装的内容

- FastAPI 路由、CRUD、分页、Pydantic 字段声明和模型 API 接入是基本功。
- 只说“集成 LangGraph”不说明如何保留契约、处理重放与持久化成本，区分度低。
- 测试数量、代码行数和八个 benchmark 任务不能直接作为复杂度或真实模型能力的证明。
- 本地路径限制不能叫恶意代码沙箱；串行单 Agent 不能叫多 Agent 协同平台。

## 待改进设计也可体现判断力

优先讨论：验收条件绑定不足、commit 后响应丢失、未知模型费用、强杀后不确定文件状态、字符预算、双引擎兼容退出策略。合理反思应说明现有边界和引入新方案的条件，不应为了“架构升级”默认添加 Redis、队列或向量库。
