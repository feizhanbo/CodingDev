# 架构决策与方案权衡

标签遵循本目录 README：D 是已有决策文档，H/C 是代码事实，I 是事后设计分析，P 是未来建议。下表的替代方案比较除明确标注外均为 I，不能称为当时做过实验。

| 决策 | 背景与约束 | 方案比较与最终实现 | 优势、代价与适用边界 |
| --- | --- | --- | --- |
| LangGraph 替代默认自研循环 | D：需要显式编排和持久状态，保留现有工具/验证及离线测试 | D：选型记录判断 LangGraph 与边界匹配，未做候选 PoC；H/C：实际拆节点调用 shared 步骤 | 更易检查路由与恢复位置；增加序列化、依赖和存储成本。适合当前本地串行任务，不证明高吞吐 |
| 保留 Custom | D：最终验收要求一个兼容发布周期 | C：设置可显式回退；resume 按 manifest 选择原运行时；不是跨引擎转换 checkpoint | 保留回退和比较基线，代价是维护两套契约/恢复路径；何时移除需使用数据与迁移政策 |
| 应用入口/共享步骤/生命周期分层 | I：CLI 与 Eval 不宜耦合 runner 内部，编排迁移不应复制规则 | C：RuntimePort/RunRequest/Outcome；每执行创建依赖；共享 steps/lifecycle | 隔离可变状态并保持契约，增加间接调用与状态投影；小型纯循环脚本未必需要这层复杂度 |
| SQLite Checkpoint | I：本地无需服务部署，需要磁盘持久化 | C：AsyncSqliteSaver + 配额包装；内存 saver 不满足跨进程恢复，远端 DB 增加部署成本 | 本地可用、易携带；写入/保留/备份仍需治理。多机器 worker 时需重新评估共享存储与锁 |
| 独立 OperationJournal | C：checkpoint 与工具文件不是共同事务 | C：prepared/completed 和摘要复用；单纯重试可能重复副作用；2PC 不适合任意文件与供应商 API | 明确拒绝不确定操作；额外 I/O、摘要成本和人工恢复负担。不是绝对一次执行 |
| 独立验收 | H：旧 verify 复用工作区 test.run；目标代码本身可变 | C：冻结基线和候选，独立测试；仅提示模型不得作弊无法强制约束 | 提升证据可信性但增加复制与测试时间；同机执行不防恶意代码；需求覆盖仍有限 |
| 全任务预算与资源所有权 | I：循环和恢复能绕过只设单次 timeout 的限制 | C：RunBudget、请求计账、Event、进程树、容量准入；各工具自行实现会容易遗漏 | 统一停止语义，平台实现复杂；不是 CPU/内存硬隔离，清理等待可能超过 timeout |
| JSON 模型协议 | C：现有领域模型和 Fake 均返回 AgentDecision | C：共享 parser、单分支校验、工具参数二次校验；原生 tool calling/严格 schema 是可选替代 | 兼容现有传输契约；自定义解析维护成本和格式失误仍在。是否实际试过其他协议待确认 |
| Service 统一事务 | H：跨 Repository 自行 commit 导致部分提交风险 | C：Repository flush、Service commit/rollback；分散提交无法整体撤销 | 事务与业务不变量一致；Service 承担事务治理，事务过长仍有锁竞争 |
| 数据库条件更新 | H/C：库存非负、状态前置条件需原子判断 | C：UPDATE WHERE 条件+rowcount；Redis 锁还需租约且不能替代 DB 事务，版本列适合更复杂并发对象 | 单库约束直接；不存在下单请求幂等、外部支付原子性。未发现真实 Redis 对比试验 |

## 有历史记录支持的性能取舍

[performance-decision.md](../../refactor-langgraph-langchain-langfuse-2026-10-29/performance-decision.md) 记录十组交替配对测量：执行中位数 Custom 65.697s、LangGraph 84.887s；中位数之比增加 29.21%，配对相对差异中位数为 37.00%，两者不可混用。文档选择为显式编排和持久恢复接受本地成本，而非声称达到事先定义的提速门槛。

本轮未重算原始 samples，以上均为 D。样本使用 Fake，包含真实编辑/测试，不能据此估计真实模型 token、生产 p95 或框架纯开销。选型文档中的审批节点等目标也不能自动当作当前实现。

## 面试最有价值的三个决策

1. 框架负责调度，业务仍掌握验收和预算：展示边界判断，不只展示 API 使用。
2. 副作用不确定时停止而不是重试：展示可靠性与可用性的明确取舍。
3. 用单库事务和条件更新解决订单不变量：展示先定义问题、再选择最小合适机制。

P：未来若业务进入多租户/恶意代码/跨机器执行，应分别补充隔离、身份与租约、共享配额、远端幂等协议；不是简单把 SQLite 换 PostgreSQL 就自动完成。
