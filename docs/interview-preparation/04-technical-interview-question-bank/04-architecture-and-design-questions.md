# 架构与技术权衡

## D01｜P0·高级｜为什么用 LangGraph，又为什么保留 Custom？

**考察**：约束驱动选型。**简答**：项目需要显式编排与持久恢复，同时保留已有工具、预算和验收。Graph 节点调用共享步骤，Custom 保留兼容和对照。

**展开**：迁移增加序列化、回执、版本身份和终态发布复杂度；共享断言验证业务契约，不说明两个引擎恢复能力完全一致。历史选型记录没有候选框架 PoC，不能说实际压测战胜所有框架；性能记录反而显示本地持久化成本增加。

**原理/追问**：何时移除 Custom？明确兼容期限、历史产物处理、回退需求，再删引擎，不能改默认值就转旧 checkpoint。

**证据**：R/J；第三阶段架构决策。**评价**：合格说明具体收益；深入承认成本与保留策略；“框架更快所以迁移”无依据。

## D02｜P1·高级｜为什么 SQLite 加回执，不只用一个数据库保存全部状态？

**考察**：事务边界。**简答**：本地 SQLite 方便部署 checkpoint，但文件修改、进程执行和远端模型不在它的事务中；回执记录可验证结果，不能创造不存在的跨资源事务。

**展开**：即使把回执搬到数据库，也还有副作用成功、回执未提交的窗口。工具可幂等化、远端幂等键、查询结果或补偿是不同解决手段。当前选择不确定时拒绝重放，适合可信本地操作。

**原理/追问**：换 PostgreSQL 就能 exactly-once 吗？不能，存储位置不是副作用协议。继续 T3 第6层。

**证据**：J；test_operation_journal。**评价**：深入区分 2PC 与两阶段记录；只讨论数据库性能偏题。

## D03｜P1·高级｜数据量或任务量增长十倍，先改哪里？

**考察**：容量拆解。**简答**：先区分大仓库、长任务、更多并发和订单写入增长；它们分别影响清单复制、上下文/产物、工作区隔离与数据库写锁，不能一律上微服务。

**展开**：当前全量扫描与候选复制需 profile，保留正确性后再考虑增量；并发需要队列准入、独立依赖、共享配额和取消策略；订单侧测事务时长/锁等待/分页。没有生产容量证据，不承诺十倍一定能支撑。

**原理/追问**：怎样验证优化等价？同输入比较 diff、状态、证据和预算语义，再看资源与时间，避免跳过验收获得假提速。

**证据**：V/B/R/D；扩展方案未实现。**评价**：合格列瓶颈；深入给测量方法和不变量；直接引入中间件没有依据。

## D04｜P0·高级｜库存为什么不先用 Redis 锁？

**考察**：最小适用机制。**简答**：当前单库库存和订单可以由条件 UPDATE 加同一事务维护；Redis 锁增加租约和跨系统故障，不能替代数据库提交原子性。

**展开**：复杂读后决策可讨论版本号乐观锁或数据库悲观锁，但应按冲突率、事务时间和数据库能力选择。这里没有实际 Redis 对比实验，只是根据当前约束分析。

**原理/追问**：库存扣减后需发消息呢？扩展可考虑事务 outbox 与消费幂等，数据库提交和消息发布不能直接认作一个事务。

**证据**：D、34e6e7e；outbox 未实现。**评价**：深入解释锁与事务解决的问题不同；“Redis 性能高所以一定用”不够。

## D05｜P1·高级｜为什么沿用 JSON 协议，不直接换严格 schema/function calling？

**考察**：兼容与可靠性取舍。**简答**：当前保持领域决策、Fake 和不同模型适配的一致接口；更强供应商结构约束可减少格式问题，但仍不能替代工具参数与业务验收。

**展开**：现有方案付出提示和 parser 维护成本。若更换协议，应验证供应商兼容、取消/usage 记录与业务契约，不把少一次 JSON 解析当作可靠性已经解决。是否历史上亲自比较过，需要本人确认。

**原理/追问**：如何用测试验证新适配？MockTransport 检查请求参数和取消、领域模型检查分支、契约测试跑相同动作；真实能力另测。

**证据**：M；test_langchain_transport。**评价**：深入能把传输与语义分开；声称当前使用严格供应商 schema 不准确。
