# 异常场景与排查

回答顺序：先说明当前行为，再列检查证据、恢复条件和未实现的改进。不要在排查前删除运行目录、改回执或重复执行副作用。

## S01｜P0·高级｜进程崩溃后恢复，发现工作区比 checkpoint 新，怎么办？

**考察**：故障窗口判断。**简答**：不能直接覆盖或重跑。检查待执行节点和操作回执，只有完成回执与当前摘要匹配才可能允许继续，不确定则拒绝自动恢复。

**展开**：先查 manifest/版本身份、可信基线和终态文件，再看 graph snapshot.next、decision_id、prepared/completed 和 after 摘要。匹配 completed 才复用结果；prepared 即使文件没变化也不能证明无副作用。异常退出与强杀都可能留下不同窗口。

**原理/追问**：日志写“成功”能代替回执吗？不能，日志不是通过恢复契约验证的结果。继续 T3。

**证据**：J，test_resume_tool_crash_window。**评价**：深入指出保护旧证据和准入条件；“删 checkpoint 再跑”危险且偏离当前设计。

## S02｜P0·中级｜模型连续给无效 JSON/工具参数，是否无限重试？

**考察**：重试分类。**简答**：解析/模型调用异常受每轮最多三次、总请求数和全局时间约束；合法 action 但工具参数错误则成为工具失败观察，不等同模型解析重试。

**展开**：请求发出前先增加次数并保存准入，SDK 重试禁用。检查 llm-requests 的状态、attempt、step 和错误类型；格式校验、未知工具、工具业务失败应分开定位。不要记录完整敏感响应到无界日志。

**原理/追问**：超时远端已完成？S03。改进可增加错误分类和退避，但不能说当前已有完整策略。

**证据**：M/B/F，ExecutionSteps.decide_step。**评价**：深入区分请求次数和工具步数；“所有失败都重试三次”错误。

## S03｜P1·高级｜模型请求本地超时，远端可能已经计费，如何恢复？

**考察**：不确定外部结果。**简答**：保留这次已消耗尝试，未知 token 不记零。已有 completed decision 可复用；prepared 请求记 interrupted/unknown，再在剩余次数内尝试。

**展开**：核对消息摘要、预算原点与 attempt，防止换上下文或重启重置计账。当前没有供应商请求结果查询，因此可能重复费用；未来需服务端请求身份与查询/幂等能力，不能单方面保证一次调用。

**原理/追问**：为何工具 prepared 停机而模型可继续？风险与操作语义不同；请求次数可保守计账，不代表远端没有执行。继续 T3 第5层分支。

**证据**：J/M，test_model_reconciliation。**评价**：明确 unknown 与零；“超时说明服务器没收到”错误。

## S04｜P1·高级｜测试通过后磁盘写满，任务还能报告成功吗？

**考察**：交付证据一致性。**简答**：不能只凭内存状态。检查 result/artifact_errors 和图终态发布；持久化失败会影响最终结果，不能吞掉错误。

**展开**：验收 suite 输出超限/超时本身应 ERROR；验收已经通过但 checkpoint/结果写失败是另一个层次。先保留已有证据，查产物配额、回执、报告摘要及是否存在 failure 诊断；不绕过配额导出无界恢复包。

**原理/追问**：能否直接重跑验证？需先确认恢复准入和已完成验证回执，不把重复验收时间当免费预算。

**证据**：B/J/V，test_terminal_publication、test_verification_receipts。**评价**：深入区分计算成功、证据持久化和发布成功。

## S05｜P1·高级｜两个任务同时修改同一工作区怎么办？

**考察**：并发范围。**简答**：当前正常执行按 run 建独立工作区，同一 run 有 OS 锁；不能因此允许不同 run 指向同一目录或外部编辑者并发修改。

**展开**：共享目录会让补丁预检、摘要和回滚互相干扰，甚至一个任务回滚另一个任务的成果。应恢复每任务隔离、禁止路径复用并保留证据；扩展共享仓库需要明确分支/worktree 和合并协议。

**原理/追问**：多机器 Worker 呢？本地锁不等于集群租约；需领取协议、fencing/去重、共享配额和持久存储。当前未实现。

**证据**：R/F/J，workspace/sandbox.py、RunLock。**评价**：合格指出竞态；深入区分同 run、不同 run 和外部进程。

## S06｜P0·高级｜库存更新成功，订单创建失败；或 commit 成功但响应失败，分别怎么办？

**考察**：部分成功与提交点。**简答**：前者若尚未提交，由 Service rollback 撤销同事务库存；后者数据库已经提交，rollback 不能撤销，需要下单请求幂等处理重试。

**展开**：当前没有请求键，所以不能承诺重试不重复下单。扩展可将业务幂等键、参数摘要和订单结果在同一事务写入，唯一约束处理竞争，相同键不同参数拒绝；不能只在进程内 set 中记一下。

**原理/追问**：成功后发通知失败？扩展 outbox/重试幂等，避免回滚已完成订单来假装跨系统原子性。

**证据**：D，test_failure_rolls_back_everything；扩展未实现。**评价**：能识别 commit 前后才算深入。

## S07｜P1·高级｜支付和取消同时到达，现有测试能证明什么？

**考察**：状态竞争与测试阅读。**简答**：当前条件状态更新与同事务回补控制合法迁移；现有命名类似“并发支付与取消”的测试实际上分别并发支付、再并发取消，不是混合竞争证明。

**展开**：若取消先提交，支付不再匹配 pending；若支付先成功，取消允许 paid→cancelled。具体锁失败/重试取决于数据库调度，不能只凭逻辑推演保证全部请求成功。应新增混合请求、锁异常和回补失败注入测试作为建议。

**原理/追问**：有真实支付网关还能这样吗？外部扣款与数据库不在一事务，需单独设计资金状态、幂等、补偿/对账。

**证据**：D，test_concurrent_payment_and_cancellation。**评价**：准确限定测试覆盖，比复述测试名更重要。

## S08｜P2·高级｜接收不可信仓库并扩展为多 Worker 平台，最先补什么？

**考察**：从当前边界做系统设计。**简答（扩展）**：先定义租户身份、执行隔离、任务领取和副作用语义，再做并发；当前路径白名单和 SQLite checkpoint 不够。

**展开**：OS/容器限制文件、网络、CPU/内存，秘密最小授权；队列租约与 fencing 防旧 Worker 继续写；独立工作区和共享配额；外部操作幂等键与结果查询。保留可信验收和取消清理，不以“加队列”替代这些协议。

**原理/追问**：租约过期旧 Worker 没死怎么办？新旧执行者需要可校验执行世代/写入凭证，远端副作用仍需幂等；单纯锁超时不能证明安全。

**证据**：R/J/F/P 是当前边界起点，新增设施未实现。**评价**：高分先识别失败模型，不能将扩展答案说成现有生产架构。
