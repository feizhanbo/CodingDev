# 两个项目的分时长介绍

以下是可口述的项目事实稿，个人经历用【待确认】留位。每个版本单独成立。时间是练习目标，不是已测朗读结果；技术词、停顿和追问会影响时长，录音后调整。5分钟版包含个人贡献段，填好前不能作为完整个人经历稿。

## DevPilot：1分钟版

我想介绍的是 DevPilot，一个本地研发任务 Agent 实验平台。它接收一个研发 Issue，读取目标仓库，形成计划，再调用工具修改代码、执行测试，并根据失败结果继续修复，最后输出代码差异和运行报告。

它主要用 Python，默认由 LangGraph 编排，LangChain 负责模型适配。我认为最值得介绍的是它对执行结果的约束：模型说完成并不直接算成功，系统会用冻结基线和独立测试验收；对于中断后的工具操作，也会检查回执，避免不确定情况下重复执行。

目前它是单 Agent、本地可信环境下的实验项目。ShopFlow 订单后端是它的目标业务仓库。我可以进一步展开可信验证或任务恢复这两个设计。

## DevPilot：3分钟版

DevPilot 面向研发任务执行，想解决的是从“模型能生成代码”到“系统能判断修改是否可信”之间的工程问题。输入是研发 Issue，输出不是一段回答，而是目标仓库的修改、测试结果、代码差异和运行证据。它目前是本地实验平台，没有包装成生产研发系统。

一次任务从 CLI 或评测入口进入应用层，为本次执行构建模型客户端、工具、状态管理和验证器，然后创建独立工作目录并冻结基线。运行过程中，模型根据任务和当前观察返回三种决策之一：调用工具、更新计划或者请求完成。工具结果会变成 Observation，下一轮模型据此决定继续修改还是验证。

技术上，LangGraph 负责节点和路由，业务规则放在共享步骤和生命周期模块中。这样保留 Custom Runtime 时，两个引擎可以共用预算、工具执行和验证规则，再通过相同的业务断言检查行为。模型适配默认使用 LangChain，但模型输出仍是项目自己的 JSON 决策协议，后端会继续校验参数和操作范围。

这里最重要的一条边界是，finish 只表示模型想结束。Verifier 会核对冻结的测试和配置有没有变化，建立候选代码副本，再独立执行测试。评测还区分 Fake 驱动的 smoke 和真实能力评估，不能把基础设施测试通过说成模型解题成功率。

另一个重点是中断恢复。图 checkpoint 保存执行进度，但文件修改不在同一个事务里，所以工具还会记录操作回执。只有结果和工作区摘要匹配才复用；状态不确定时会停止自动重放。这个方案宁可保守一些，也不假装所有中断都能无损恢复。

项目同时控制全任务时间、请求次数和测试进程生命周期。它的价值主要是把模型决策放进可验证、可停止、可追溯的后端流程；局限是自然语言条件仍有未覆盖部分，也没有恶意代码隔离或分布式执行能力。

## DevPilot：5分钟版

DevPilot 是一个本地研发任务 Agent 实验平台。它的输入是研发 Issue，处理过程包含仓库探索、计划、代码修改、测试和失败修复，最终产出 Diff 与运行报告。项目关注的是工程执行闭环：模型可能给错代码，也可能过早认为自己完成了，所以系统需要明确谁做决策、谁执行，以及谁确认结果。

整体上，CLI 和 EvalRunner 通过 ApplicationRuntime 进入系统。应用层为每次任务构建独立依赖，建立工作目录和可信基线，之后交给运行时推进。默认编排是 LangGraph，模型适配是 LangChain，同时保留 Custom 和 OpenAI 兼容路径。领域状态记录任务进展，图状态记录调度与恢复所需的信息，这两者没有简单合成一个状态字段。

模型每次输出 action、plan_update 或 finish 中的一种。动作进入 ToolRegistry，由工具自己的输入模型校验参数，再执行路径、写保护和资源限制。文件读取、搜索、补丁和测试产生的结果，会作为 Observation 返回状态。上下文构建器保留任务、最新计划和当前失败信息，对较早观察做规则压缩。这里不是 RAG 或长期记忆，而是单次运行内如何保留必要证据。

第一个值得展开的设计是独立验收。项目不直接相信模型 summary，也不只依赖开发过程中一次 test.run 的输出。执行前会冻结文件基线，对原有测试和配置建立保护；请求完成时，重新核对真实文件变化并生成候选副本，用独立测试环境验证。这样新增一条简单测试不能掩盖旧测试失败，未跟踪文件和删除文件也能被纳入检查。不过测试通过仍不等于所有自然语言需求都已证明，未绑定检查的条件会保留为 uncovered。

第二个是恢复一致性。工具可能已经改了文件，但图还没保存下一份 checkpoint。如果直接重跑节点，可能重复副作用。项目在执行前记录 prepared，执行后记录 completed、工作区摘要和结果摘要；恢复时只有这些信息匹配才复用结果。只留下 prepared 时拒绝自动重放。这不是 exactly-once，而是明确哪些操作能够安全继续、哪些需要检查。模型请求又有单独的账本：超时可能已经计费，所以保留尝试次数，未知用量不填成零。

第三个是资源治理。任务有整体截止时间和累计验证预算，恢复不重置预算。测试和 Git 命令通过共享进程执行器管理；协程取消后通知同步 worker，等待进程树和 I/O 清理，再向外传播取消。因此设置超时不等于到点立刻返回，也不等于 CPU、内存硬隔离。

框架迁移也有代价。当前通过共享步骤和业务契约测试保持主要行为，但图持久化增加存储和执行开销，还带来依赖版本与恢复身份检查。历史测量记录接受了这个本地成本，不能将迁移表述成提速。

我在其中实际参与的是【待确认：模块与参与方式】。具体可以用【待确认：一次亲自完成的改动】说明：当时观察到【现象】，通过【日志或测试】定位到【原因】，我承担了【设计/实现/验证动作】，最后以【断言或产物】确认结果。这段需要按真实经历填写，不能从代码作者直接推断。

目前已具备本地闭环、独立验证、恢复回执和预算控制；真实模型效果、多租户隔离、集群调度和生产容量不在已确认成果里。如果继续推进，我会先补重要验收条件的显式检查，再根据真实使用场景决定是否需要更强隔离与并发架构。

## ShopFlow：1分钟版

ShopFlow 是一个用 FastAPI、SQLAlchemy 和 SQLite 实现的订单后端，也是 DevPilot 修改和评测的目标项目。它提供客户、商品、订单和优惠券相关能力，支付只是订单状态模拟，并没有接真实资金系统。

我会重点介绍它的数据一致性设计。创建订单时先合并重复商品数量，通过条件 UPDATE 扣库存，再创建订单和明细，由 Service 统一提交事务；任何提交前的步骤失败都回滚。取消订单也先通过状态条件更新，只有真正迁移到 cancelled 的请求才回补库存，重复取消不会重复加库存。

它适合展示事务边界和并发状态控制，但没有生产高并发数据，也没有完整的下单请求幂等机制。

## ShopFlow：3分钟版

ShopFlow 是 DevPilot 的业务目标仓库，用一个规模可控的订单后端承载功能、Bug 和性能类研发任务。它不是已投入商业运营的电商系统，但业务里有库存、订单明细、优惠券和状态流转，足以检验跨层修改是否正确。

代码分成 API、Service、Repository 和数据库会话。API 处理输入及 HTTP 错误，Service 负责业务规则和事务边界，Repository 负责查询与更新。每次请求获取 Session，用完关闭；需要成功提交的业务由 Service 明确 commit。

创建订单时，先校验客户、订单明细和数量，把重复商品合并后再处理库存。关键点是库存判断不只在 Python 里先读再减，而是放进数据库 UPDATE 条件：只有扣减后仍非负才更新，并检查影响行数。扣库存、创建订单和明细放在同一事务中，因此后面的商品或明细失败时，可以整体回滚。

这个设计在 Git 历史中有明确变化。旧 Repository 会自己提交，后续步骤失败可能留下部分成功；改造后 Repository 只 flush，Service 最后提交。测试也不只是验证正常下单，而是在第二件商品、明细写入后以及提交前注入失败，检查库存和订单记录是否保持一致。

状态流转也是类似思路。支付只允许 pending 到 paid；取消允许 pending 或 paid 到 cancelled，只有状态真正改变才回补库存。重复取消可以返回已取消状态，但不再次回补。它解决的是该状态副作用的重复执行，不等于所有接口都有请求级幂等。

当前限制也比较明确：SQLite 并发写能力有限，锁冲突要处理；金额仍使用浮点数；下单提交成功但客户端没收到响应，重试可能产生重复订单。所以这个项目适合讲清楚单库事务和状态控制，而不是描述成分布式支付系统。

## ShopFlow：5分钟版

ShopFlow 的定位是一个本地订单后端，同时作为 DevPilot 的目标仓库。它把客户、商品、订单、明细和优惠券组织成一套可测试的业务，让 Agent 的修改不局限于一个孤立函数，而是涉及接口输入、业务规则和数据持久化。支付与取消也是状态模拟，没有真实商户或支付渠道集成。

技术栈是 FastAPI、SQLAlchemy、Pydantic 和 SQLite。API 层接收请求与映射错误，Service 层协调业务，Repository 层做具体查询和更新。数据库依赖每请求创建 Session，并在结束后关闭。这里特意区分了关闭会话和提交事务：资源释放不能代替业务成功时的 commit。

先看创建订单。输入不能是空明细，数量必须是正整数；同一商品可能在请求里出现多次，所以先按商品 ID 汇总。否则逐行判断库存，会让每一行看起来都够，但合起来超过可用量。校验客户和商品后，记录下单时的单价并计算金额，再处理优惠券、订单与明细。

真正的并发控制点在库存 UPDATE。语句把 stock 加上负的购买数量，并要求结果不能小于零。判断和修改在数据库执行，而不是把之前查询出来的旧库存直接写回。应用根据 rowcount 判断是否成功，再决定是否继续。即便这条 UPDATE 成功，也还没有独立提交；它要和订单、明细一起完成。

历史改造最有代表性的部分就是提交点。旧实现里 Repository 各自 commit，订单创建成功后再扣库存，如果后面失败，前面已经提交的部分无法撤销。现在 Repository 用 flush 发送 SQL、取得订单 ID，Service 在所有步骤完成后 commit，异常时 rollback。这样业务不变量与事务范围一致。它不是引入了更复杂的中间件，而是把原本分散的责任放回合适的层。

取消订单还需要防止重复回补。当前先执行带 expected status 的条件更新，只有 pending 或 paid 能迁移成 cancelled。真正更新成功的请求才遍历明细还库存；后续重复取消看到已经 cancelled，就返回状态，不再加库存。状态变更和库存回补在同一事务，因此回补失败也不会留下单独已提交的取消状态。支付同样通过 pending 条件更新，但重复支付返回冲突，不能将其说成按请求键复用响应的完整幂等机制。

测试上，除了正常流程，还在第二件商品扣减、明细 flush 后和 commit 前注入异常，检查库存恢复、订单和明细没有留下半成品。也有并发下单、并发支付以及并发取消测试。不过有一个容易讲错的地方：相关测试是分别并发支付，再并发取消，不是支付与取消混合竞争的完整验证。

我的实际参与范围是【待确认：业务模块、事务改造或测试工作】。如果本人确实参与这次改造，可以展开【亲自复现的失败输入】、【定位过程】和【本人完成的修改与测试】；如果只是后续分析和学习，应准确说明这一点，不把提交记录自动转成独立开发经历。

这个方案的边界是单库事务。SQLite 仍可能发生写锁竞争；金额精度和下单请求幂等还需要改进。特别是 commit 已经成功、响应却丢失时，rollback 不能撤销订单，重试需要独立的幂等键和结果复用设计。未来如果接真实支付，还要处理远端扣款和数据库之间的对账，而不是扩大本地事务就能解决。

我会把它作为后端基本功的具体案例：先明确业务不变量，再选择数据库条件更新、事务边界和测试证据，而不是一开始就把问题包装成分布式架构。
