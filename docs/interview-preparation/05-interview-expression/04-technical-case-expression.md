# 七个案例的三层表达

每例先讲简版，面试官要求再展开。30–60秒、1–2分钟是练习窗口，需按本人语速计时；不要为了填满时间重复背景。完整版本末尾的【本人动作】仅在贡献确认后补入，未确认时保持“项目”主语。源码定位统一见[索引](../02-core-technical-deep-dive/source-index.md)。

## C1：编排迁移，保留业务契约

**简洁表达｜30–60秒**

这个案例的重点不是接入 LangGraph，而是更换编排方式时保留原有规则。项目把预算、工具和验收放在共享步骤里，图负责推进流程，Custom 作为兼容路径保留。两边复用业务断言检查行为。这样迁移有明确边界，不过也增加了持久化和双引擎维护成本，不能说换框架就更快。

**完整表达｜1–2分钟**

DevPilot 原来已有自研执行循环和工具、验证逻辑，引入图运行时后，真正需要保证的是“同样的任务不会因为换了编排器就跳过预算或验收”。所以项目先建立应用入口契约，再抽出共享步骤和生命周期；LangGraph 用节点调用这些服务，而不是把整个旧循环包成一个节点。

每次执行会重新构建依赖，避免运行状态串到其他任务。旧任务恢复也按 manifest 选择原引擎，不使用当前默认值硬套。测试通过替换 runner 构建边界复用原有规划和修复断言，图恢复则另测。历史测量承认持久化成本增加，因此这个案例体现的是语义保持和回退设计，而不是提速。【本人动作待确认：负责哪层接口、节点或契约测试。】

**深入表达**

可以沿 ApplicationRuntime.execute→bootstrap→RuntimeLifecycle→Graph节点追踪。GraphState 的 domain/accounting 是序列化投影，客户端和锁留在运行依赖中。shared steps 执行业务，节点路由处理 action/plan/finish；manifest 管恢复身份，checkpoint 管进度。两套引擎共用业务不代表恢复能力相同。证据：41c4ea5、test_graph_business_contracts；接第四阶段 T1。

## C2：让完成声明经过独立验收

**简洁表达｜30–60秒**

Agent 既能改代码又能说自己完成，如果只相信它的测试输出，成功口径就不够可靠。项目在执行前冻结基线，请求结束时建立候选副本并独立测试；原有测试和配置不能被模型随意修改。这样可以核验具体修改和测试证据，但没有检查覆盖的自然语言条件仍然不能说已满足。

**完整表达｜1–2分钟**

这部分想解决的不是模型永远不出错，而是错误不能轻易变成“任务成功”。原来的验证会复用工作区测试，后续改成先核对冻结基线，再根据真实文件清单物化候选。测试和配置属于保护对象，新增测试与基线测试分开运行，因此加一条简单测试不能覆盖旧测试失败。

Verifier 的结果回到 Runtime，拒绝时继续修复，并受重试和时间预算限制。评测同时区分 Fake smoke 和能力评估，未测项保持未测，不包装成成功率。相关测试覆盖删除测试、未跟踪文件和新增测试不能掩盖旧失败等情况。局限是独立目录不是OS隔离，而且测试通过仍有需求覆盖边界。【本人动作待确认：保护策略、候选物化或验证用例。】

**深入表达**

沿 capture_snapshot→check_integrity→materialize_candidate→TaskVerifier.verify→run_independent_suite 展开。文件并集比较检测新增/删除，no-index diff 不依赖工作区是否已跟踪；harness 控制pytest配置。coverage_for 的关键词映射有限，checks通过不要求所有coverage verified。证据：4a8a778、test_evidence；接 T2。

## C3：checkpoint之外的副作用恢复

**简洁表达｜30–60秒**

图保存了状态，不代表文件修改也能一起回滚。工具执行成功但checkpoint没保存时，重新执行可能产生重复副作用。项目增加操作回执：执行前记prepared，完成后保存结果与摘要，恢复时匹配才复用。只留下prepared就不自动重放。这是保守恢复策略，不是exactly-once。

**完整表达｜1–2分钟**

这个问题最难的是区分“没有完成”和“完成了但没记下来”。文件操作与SQLite图状态没有共同事务，所以只恢复图会漏掉外部效果。项目让每个工具操作有稳定身份，执行前持久化意图，完成后记录后置工作区和结果摘要。

恢复时，不只判断文件存在，还核对参数、回执阶段、当前工作区和结果。如果已经完成且一致，就复用结果，不再调用工具；如果结果不确定，就停下来检查。测试覆盖了回执落盘前后中断和结果变化等窗口。代价是部分任务不能自动继续，但比盲目重复写入更符合当前边界。模型请求另有对账策略，未知费用保留未知。【本人动作待确认：回执设计、恢复分支或故障注入。】

**深入表达**

LangGraph runner 的execute_tool先Journal.begin，再共享执行步骤，最后complete；resume先验证manifest和基线，再检查是否存在允许工作区前进的completed回执。prepared并非2PC prepare，没有协调者能回滚远端API。副作用成功与complete之间的窗口仍存在。证据：operations.py、test_resume_tool_crash_window；接 T3/S03。

## C4：预算与异步资源所有权

**简洁表达｜30–60秒**

Agent不是一次模型请求，单次超时无法限制整个修复循环。项目用全局截止时间、请求次数和累计验证时间约束运行，恢复也不重置预算。子进程则由统一执行器管理，取消后先通知worker停止并等待清理，再返回。这样明确了谁负责资源，但不等于CPU、内存硬隔离。

**完整表达｜1–2分钟**

这里需要处理两件事：任务最多消耗多少，以及到限后实际工作是否停止。RunBudget贯穿准备、模型、工具和验收，把各阶段可用时间限制在全局剩余量内。模型失败重试也计数，恢复保留原来的截止时间和已用预算。

在资源层，取消await不会自动杀线程，更不会保证pytest的后代进程退出。项目用Event通知同步worker，等待进程树和I/O清理后再传播取消；Windows下使用Job管理后代。测试检查取消等待清理、输出上限和父子进程退出等行为。这意味着超时后的返回可能晚于设置值，不能宣称绝对准时强杀所有工作。【本人动作待确认：预算传播、进程执行器或测试。】

**深入表达**

沿 decide_step准入→DecisionService.wait_for→run_cancellable→run_process追踪。shield保护worker，取消时set Event，继续等待并重新抛CancelledError。RunBudget.evaluation在finally累加时间，恢复取保存余量与原截止时间剩余量的较小值。证据：budget.py、processes.py、test_processes；接 T4。

## C5：受控工具与文件修改

**简洁表达｜30–60秒**

模型生成的路径和补丁都需要校验。项目先通过Registry验证参数，再检查最终路径和受保护文件，用Git解析实际修改目标，预检查后才应用。普通异常尝试恢复原文件，强杀则交给恢复机制判断。这里的价值是约束文件副作用，不能称为完整安全沙箱。

**完整表达｜1–2分钟**

文件操作的风险不只是补丁语法错误，还有路径越界、修改验收测试和应用失败留下半成品。项目把这些检查分成几层：工具名和参数模型限制入口，PathGuard检查规范化后的路径，冻结策略保护测试与配置，Git numstat给出实际目标清单。

应用补丁前保存原文件并控制回滚内容大小，先check再apply；普通异常会尝试还原。历史上删除目录的校验也修正过，从检查一个相关父目录改成检查规范化后真正目标的父目录，回归测试断言危险输入不会调用删除。局限是预检与应用之间有竞态，强杀不会执行Python回滚，宿主恶意代码也不在防护保证里。【本人动作待确认：具体路径或补丁变更。】

**深入表达**

ToolRegistry→input_model→PathGuard/validate_write→git apply --numstat→保存bytes→--check→apply。异常恢复是尽力操作，磁盘满也可能影响回滚；最终验收以实际文件清单为准，不只信工具modified_files。证据：dccd2ba、ApplyPatch.execute、test_patch_atomicity；接 T5。

## C6：订单事务与一次回补

**简洁表达｜30–60秒**

ShopFlow需要让库存扣减和订单创建一起成功或失败。项目把提交放到Service，Repository只flush；库存用条件UPDATE避免按旧读值扣减。取消先做状态条件迁移，只有迁移成功才回补库存，所以重复取消不重复加库存。它解决单库业务一致性，不代表已实现完整请求幂等。

**完整表达｜1–2分钟**

这个案例有清晰的前后变化：旧Repository各自commit，后面某件商品扣减失败，前面的订单或库存可能已经提交。改造后先合并重复商品数量，条件扣库存，创建订单和明细，再由Service统一commit；异常时rollback。

取消同样不能先查状态再无条件还库存，而是先争取pending或paid到cancelled的迁移资格，只有成功的请求回补。测试在第二件商品、明细flush后和commit前注入失败，检查没有半成品，也检查重复取消只恢复一次。当前仍缺下单请求幂等；commit成功但响应丢失后，rollback帮不上忙。【本人动作待确认：事务改造或对应回归测试。】

**深入表达**

API→OrderService→update_stock的stock+delta>=0条件→Repository.create的flush→Service.commit。rowcount决定匹配是否成功，但锁异常仍需处理。cancel_order在同事务里完成状态变化和回补；现有并发支付/取消测试分两个同类阶段，不能称混合竞争已验证。证据：34e6e7e、test_order_integrity；接 T6。

## C7：上下文保留当前事实

**简洁表达｜30–60秒**

上下文管理不只是把历史变短。项目需要确保模型看到最新测试结果和仍未解决的验收失败，避免旧错误干扰下一步。它分别记录修复来源，压缩旧观察，保留必要失败信息；固定内容仍超预算时停止。这个方案可重复，但字符预算不是精确token计数，也不是长期记忆。

**完整表达｜1–2分钟**

Agent运行几轮后，历史观察会增长，早期失败也可能已经被后续测试解决。如果只是把所有日志拼进去，既浪费上下文，也会让模型反复修旧问题。当前ContextBuilder把任务、计划、当前阶段和观察组织成消息，对旧观察做规则摘要，近期结果保留较多信息。

测试成功会覆盖旧的当前测试失败提示，但独立验证拒绝有自己的repair_source，不能被一次开发测试成功清掉。硬预算在状态副本上删可删除观察，保护必要反馈，不修改真实历史。仍放不下就报超限，而不是把任务要求静默删掉。测试确认最新结果的表达，但没有据此声称模型修复率提高。【本人动作待确认：反馈字段或压缩策略。】

**深入表达**

observe_step→StateManager.apply_tool_result/set_repair→ContextBuilder._build_state_content→_enforce_limit→prepare_messages最终检查。历史41b027b增加硬预算并修正verification_failed/message字段识别；字符和token不等价，规则摘要也有损。证据：test_context_feedback、test_context_compression；接第四阶段 A03/A07。
