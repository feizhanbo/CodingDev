## 二、项目背景中的差异

### 1. “参考 Claude Code 相关源码”是经历声明，当前无法核实

当前能核实的是：项目确有自行编写的 CustomAgentRunner、StateManager、LoopGuard、ContextBuilder 和工具类。没有找到将某份 Claude Code 资料、特定版本或源码机制映射到本项目实现的记录。不能因为架构包含计划、工具和观察，就反推参考了某一项目的源码。

**建议**：若确有这段经历，可保留并准备具体参考材料与机制说明；若只是阅读文章或使用产品，改为“参考 Coding Agent 的执行机制，自主实现 Python 编程代理原型”。本核查不替用户编造源码学习经历。

依据：`devpilot/devpilot/runtime/custom/`、`devpilot/devpilot/agents/developer.py`；对当前源码、测试、脚本、README/设计文档的相关关键词检索。

### 2. “重点实践 MCP、Skills”把学习目标写成了实现成果

任务编排和工具调用确已实现；MCP 和 Skills 则没有对应可执行链路。作为未来研究目标可以出现，但与后面明确写成完成态的两条“实现内容”组合，会形成事实误导。

**建议**：背景写“当前重点实践任务编排、工具执行、上下文管理与可信验收；后续计划研究 MCP 和 Skills”。

### 3. “通过实际开发对比 ReAct 和 Plan-and-Execute”缺乏实现及实验支撑

当前只有一套 CustomAgentRunner。每轮由同一 DeveloperAgent 根据上下文返回 action、plan_update 或 finish；计划更新和工具执行共享同一个循环。`_maybe_advance_phase` 根据工具类别与步数启发式切换阶段。

未发现两个可切换的运行策略、独立 Planner/Executor 执行路径、按计划逐步调度器、同任务同模型的两模式实验配置或结果对照。`tests/test_planning_flow.py` 测的是同一运行器中的计划更新，不是两种算法的对照实验。

**可以描述为**：“实现支持显式计划更新的逐轮决策执行循环。”从行为看它具有动作—观察式循环特征，但这只是代码结构判断，不应称为严格复现某个算法或已完成双模式比较。拥有 plan_update 不足以证明独立 Plan-and-Execute 架构。

依据：`runtime/custom/runner.py::run/_maybe_advance_phase`、`domain/decision.py::AgentDecision`、`agents/developer.py::decide`、`tests/test_planning_flow.py`。

## 三、Agent 闭环与上下文管理的差异

### 4. “自主实现 Runtime”成立

CLI 明确初始化自定义运行器，连接 LLM、上下文、状态、工具、护栏、工作区、验收器和追踪器；不是只调用某个外部 Agent 框架。此项应保留。

依据：`cli.py:138 initialize_components`；`runtime/custom/runner.py:119 run`。

### 5. “管理计划进度”应限定为保存和展示模型上报状态

ImplementationPlan 有目标、步骤、状态和 revision；运行器收到 plan_update 时直接替换 state.plan，上下文再展示这些步骤。没有把工具结果绑定到某个 plan step 的自动状态推进、步骤依赖调度或逐条验收。

**差异**：实现了计划数据管理，不是独立的计划执行引擎；步骤完成标签主要是模型的报告，不是运行器证明。

建议改为：“维护任务阶段、模型生成的实施计划及工具观察记录”。依据：`domain/plan.py`；`runner.py` 的 `state.plan = decision.plan_update`；`context.py::_build_state_content`。

### 6. “完成探索—规划—修改—修复—验证闭环”作为运行机制成立，作为普遍能力保证不成立

源码有对应路径，FakeLLM fixture 还会真实改错、运行 pytest、修复和再验收。但运行器允许跳过 planning，阶段并不是强制顺序；普通任务也不保证一定触发测试失败修复。

本地只找到一份 smoke/PASS 的 eval_result，没有真实 capability 结果。固定决策演练证明链条能执行，不证明真实模型能自主完成全部开发任务。

建议写“串接上述执行链路，并通过固定决策冒烟和本地测试验证编排行为”，不要写成已有广泛真实任务成功结果。依据：`cli.py::create_fake_client`、`runner.py::_maybe_advance_phase`、`evals/runner.py::run_eval`。

### 7. 预算、重试、重复检测已实现，但不能写成完全可靠的执行上界

有 max_steps、max_test_retries、max_modified_files、max_patch_failures 等配置和检查。差异在于：

- `AgentDecision` 三个字段都可为空，`{}` 可被接受；空决策不产生工具/计划观察，步数不增，LoopGuard 也不累积无动作计数，因此存在持续请求模型的缺口。
- 注册表接受下划线工具别名，但部分专用失败处理只匹配点号工具名；例如 test_run 的失败不会进入仅匹配 test.run 的重试分支。
- 限制主要是步骤与测试重试，不包含独立总请求数、总运行时长或费用硬预算。

因此“设置了预算与护栏”准确，“保证不会无限循环/严格控制成本”不准确。依据：`domain/decision.py`、`runtime/custom/loop_guard.py`、`runner.py:148/438/482/511`、`tools/registry.py::get`。

### 8. “结构化上下文注入与阶段摘要”成立，但实际是规则摘要和截断

ContextBuilder 注入固定系统规则、工具 Schema、完整任务、当前计划、阶段提示及观察。默认保留最近 10 条较完整观察，旧观察按工具、文件、测试和失败生成规则摘要，工具结果还按字符截断。

没有用模型生成的长期语义记忆，没有基于任务激活外部知识包，也没有证明摘要后关键信息始终保留。建议用“近期观察保留、历史观察规则摘要与工具结果截断”，比泛称高级上下文管理更具体。

依据：`runtime/custom/context.py::build/_summarize_observations/_build_progress_summary/_format_observation_data`。

### 9. “控制上下文膨胀”是机制目标，不是已验证的硬限制或优化收益

30000 是字符触发阈值，不是模型 Token 窗口；压缩将近期观察从默认 10 条缩至 8 条，保留完整任务、计划和旧摘要，不对最终输入做严格上限校验。工具说明在 ContextBuilder 和 OpenAIClient 中还会重复注入。初始化时未向 ContextBuilder 传入 trace_writer，压缩事件默认未接通。

尚无“减少多少 Token”“长任务成功率提高多少”的对照证据；不应自行补充数字或声称解决上下文爆炸。依据：`context.py:439 _compress_context`、`llm/openai.py::chat`、`cli.py::initialize_components`。

## 四、Tools 与工作区隔离的差异

### 10. 八项工具确实存在，但原文列举漏掉代码补丁

| 实际工具 | 职责 |
|---|---|
| repo.list_files | 文件列表 |
| repo.search_code | 代码搜索 |
| repo.read_file | 文件读取 |
| code.apply_patch | 修改现有代码的补丁应用 |
| code.create_file | 新建文件 |
| test.run | pytest 执行 |
| git.status | Git 状态 |
| git.diff | Git 差异 |

原文把 Git 状态和差异分开也只有七项明确操作，漏掉了最关键的 code.apply_patch。建议完整列明八项；称“八项工具”比“八类工具”更精确。依据：`cli.py:81 register_all_tools`。

### 11. “操作真实项目”应说明是副本和 Python/pytest 场景

工作区复制真实目标文件并 init 新 Git 基线，工具操作具有真实文件效果；但修改不会自动回写原仓库。默认提示写死 ShopFlow 架构，测试工具只运行 pytest；换 base_repo 不代表已适配任意语言和构建系统。

建议写：“在目标 Python 项目的独立副本中执行代码修改和 pytest，并保留差异供人工审阅。”依据：`workspace/sandbox.py::create`、`tools/test/run_tests.py::execute`、`llm/prompts.py::REPOSITORY_INSTRUCTIONS`。

### 12. “任务级文件隔离”在副本层成立，安全隔离含义偏强

每次任务有独立 workspaces/run_id/repo，PathGuard 校验工具显式路径，避免正常操作直接写原项目。但测试代码运行在宿主机进程中，没有容器/系统权限隔离。普通复制发现 symlink 只警告；目录搜索只校验根路径，不逐文件应用禁止规则。

因此不能扩写成“安全执行任意不可信代码”“完全阻断越界和密钥访问”。建议限定为“工作区副本隔离与工具路径约束”。依据：`workspace/sandbox.py::create`、`tools/path_guard.py`、`tools/repo/search_code.py::execute/_run_rg/_python_search`、`evals/benchmark.py::run_independent_suite`。

### 13. “轨迹、日志支持回溯定位”成立，不等于可重放和恢复

已有 trace.jsonl、测试日志/XML、state.json、result.json、final.diff 等。trace 的工具结果只保留部分摘要，最终状态主要在结束时落盘；没有 resume 命令。原文“回溯与定位”可以保留，但不能延伸为“完整重放”“断点恢复”。依据：`tracing/writer.py`、`runner.py::_trace/_save_artifacts`、`cli.py::inspect/diff`。

## 五、MCP 描述与当前实现的直接矛盾

### 14. 没有标准 MCP Server，也没有 tools/list 协议入口

当前 `ToolRegistry.list_schemas()` 是一个进程内 Python 方法，返回 name/description/input_schema 列表。它不是网络或 stdio 协议方法 `tools/list`。没有找到 MCP 初始化握手、服务传输、协议请求分发、tools/call 或 MCP Server 启动入口。

不能因为工具有 JSON Schema，就认定已经封装 MCP。`llm/tool_schema.py::tools_to_openai_format` 做的是 OpenAI 风格 Schema 转换，也不是 MCP 协议。

依据：`tools/registry.py:76 list_schemas`；`llm/tool_schema.py`；`pyproject.toml` 及有效源码与测试全量检索。未发现 MCP 依赖只是辅助证据，主要依据是当前调用链。

### 15. 没有 MCP Client 动态发现，工具由 CLI 静态构造

真实路径为 `register_all_tools → registry.register(具体工具实例) → registry.execute → tool.execute`。初始化直接 import 工具类，调用模型前再把这些本地实例的描述导出到提示中；没有连接外部 Server 或动态获取工具列表。

**原文“Agent 通过 MCP Client 动态发现工具能力”应删除。** 若想写当前实现，可改为“通过 ToolRegistry 统一注册、Schema 导出、参数校验和执行分发，降低运行循环对单个工具实现的直接依赖”。

### 16. “工具解耦与跨应用复用已实现”超出现有证据

Tool 基类和 Registry 确实提供一定接口抽象，不是全无解耦。但 CLI 仍静态 import 八个类，runner 对 repo/code/test 工具名有特殊判断；工具上下文也依赖 workspace/run/artifacts/trusted 等项目约定。未找到第二个应用通过标准协议接入工具的案例。

应区分“具备进程内扩展接口”与“标准协议跨应用复用”。依据：`tools/base.py`、`tools/context.py`、`cli.py::register_all_tools`、`runner.py::_maybe_advance_phase`。

## 六、Skills 描述与当前实现的直接矛盾

### 17. 当前没有项目内 Skill 包或完整加载链

在排除 .git、虚拟环境、构建产物和运行副本后，没有发现项目自己的 SKILL.md 能力包、Skill 元数据索引、目录发现器、激活规则或按需读取实现。当前 system/policy/repository instructions 是 `llm/prompts.py` 中的静态常量，在每次上下文构建时组合。

当前会话运行环境向审计助手提供的 Skills，不属于 DevPilot 产品代码，不能作为项目已经支持 Skills 的证据。

### 18. 静态 Prompt、历史观察摘要不等于 Skill 渐进式加载

渐进式加载的成果需要能追踪“发现能力元信息→按任务选择→读取完整指令→必要时读取支持资源”的实际链路。目前只有固定 Prompt 和已执行工具观察的压缩，处理对象和触发机制不同。

**原文“参考 Agent Skills 标准封装独立 Skill 包，采用渐进式加载策略”应整体移到未来计划。** 本次没有必要用外部标准的更多细节掩盖当前根本不存在加载链这一事实。

### 19. 所举三类 Skill 都没有对应产物，多工具调用也不是 Skill 编排

Ruff 出现在开发脚本/CI 中，不是 Agent 可激活的“规范检查 Skill”；新增测试由模型经 code.create_file 完成，不是“测试生成策略 Skill”；系统只提供 git.status/git.diff，不提供提交工具，也没有“Git 提交规范 Skill”。同一任务连续调用多个 Tool，只能证明代理能编排工具，不能证明由 Skill 包驱动组合。

依据：`llm/prompts.py`、`cli.py::register_all_tools`、`dev.ps1`、`.github/workflows/ci.yml`、当前文件清单。

## 七、可信交付与指标描述的差异

### 20. 冻结原测试、禁止篡改、允许新增和独立验证确有实现

`capture_snapshot` 在首个动作前保存原文件和哈希；`validate_write/check_integrity` 保护既有测试与配置；`materialize_candidate` 计算文件级真实新增/修改/删除；TaskVerifier 分开运行冻结原测试及新增测试。最终验收还要求非空差异、修改范围等条件。该条是描述中证据较充分的部分，应保留。

“冻结”是文件副本与哈希校验，不是只读挂载或宿主安全权限。当前机制防常见测试篡改，但并不阻止候选 Python 代码使用宿主权限；也不是所有文件类型都纳入 inventory（例如运行目录及数据库文件被跳过）。

依据：`verification/evidence.py::capture_snapshot/validate_write/check_integrity/materialize_candidate`、`verification/verifier.py:44 verify`。

### 21. 验收通过不等于通用业务需求全部完成，交付也没有自动 PR

普通 run 的验收是完整性、差异和测试检查，仅用少量关键词判断是否要求新增测试；没有任意自然语言验收标准逐条判定。内置 eval 另有隐藏测试，但覆盖范围是固定八项任务。结果交付是工作区、diff 和报告，不包括 PR、合并或发布。

原文“交付校验流程”可以保留；若写“完整自动研发交付”应明确到代码产物与测试验收这一边界。依据：`verification/verifier.py::verify`、`evals/runner.py::run_eval`、`cli.py` 命令集合。

### 22. 四项核心指标的实际落地程度不同

| 原文指标 | 当前实现 | 描述差异 |
|---|---|---|
| 任务成功率 | EvalResult 区分 PASS/FAIL/NOT_EVALUATED/ERROR，区分 smoke/capability；summary 统计数量与有效覆盖 | 有成功率计算所需的基础结果，但 summary 主要展示计数和覆盖，并非长期统计平台；当前没有真实 capability 结果支撑具体比例 |
| 测试通过率 | visible/hidden pass_rate，基于结构化结果 | 已实现；缺证据用 null，不应写成未测也通过；原测试通过不能代表需求通过 |
| 平均步数 | EvalResult.avg_steps 直接赋值 run_result.total_steps | 字段名为 avg，实际是单次运行步数；summary 没有跨任务/多次试验的平均值计算 |
| Token 消耗 | LLM usage 经请求记录→MetricsCollector→result.json/llm-requests.json | 有运行级采集；未知 usage 保留 null；EvalResult.token_cost 未赋值，评测汇总不展示 Token，也无金额折算 |

依据：`evals/runner.py::EvalResult/run_eval/generate_summary/generate_comparison_table`；`tracing/metrics.py:55 to_dict`；`llm/openai.py::chat`；`runner.py::_save_artifacts`。

### 23. “持续迭代 Agent 表现”没有可复核的效果对照

重新扫描当前 `runs/` 和 `devpilot/runs/`，只找到一份 smoke/PASS 的 eval_result；没有 capability eval_result。不能因此断言没有做过仓库外实验，但当前证据不足以支持“以真实任务成功率持续迭代并已取得效果”的成果表达。

已有八项基准、自检、隐藏测试和 Token 记录是重要基础。必须区分：单元测试证明确定性实现行为；FakeLLM 证明预制决策能跑通；参考补丁自检证明数据集有效；真实模型 capability 才能证明模型在该任务上的实际表现。这四者不能互换。
